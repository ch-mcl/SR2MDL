## 解読結果

メモの構造の主張は正しかった。Node Relation の +0x00 が子、+0x04 が兄弟。
コードは同じフィールドを Parent / Child と誤って命名していたので、
Child Offset / Sibling Offset に改名した。

メモの表記のうち2点を訂正(メモ本文に追記済み)。

- 列見出しの `0x68` / `0x6C` は実際には **0x08 / 0x0C**。
  それぞれ Node Index と Texture Index。
- `NodePointer[43]` は **Road[43]**。road配列は Relation Offset + 0x20 から始まり、
  DES_SS1.DAT では 0x1D4D00 + 43*0x60 = 0x1D5D20。その +0x04 が Node Offset。

road は兄弟連鎖の先頭を指しており、先頭しか読んでいなかったため
レベルの大半が欠落していた。子・兄弟を辿るようにして到達ノードが大幅に増えた。

### 子・兄弟の再確認 (DES_SS1/cp_4.mdl)

+0x00 が子で正しい。cp_4.mdl はノード2個で、node_0001 は (0,0,0) 格納だが
ゲーム中は node_0000 と同じ位置・角度に出現し、node_0000 を動かすと追従する。
兄弟なら自分の位置(ワールド原点、node_0000 から845離れた場所)に留まるので、
この挙動は子でしか成立しない。

裏付けとなる統計 (サンプル140ファイル)。

- どちらの辺も、同じノードを2箇所から指すことが一度も無い。
  first-child / next-sibling 木として整合する。
- 車は「根1個 + その下に横一列」。r_corolla は node_0000(ボディ) -0x00-> node_0001、
  node_0001〜node_0009 が -0x04-> で連なり、node_0009 -0x00-> node_0010。
  0x00 が2本、0x04 が8本、ノード11個、根1個。
  ホイールが原点のボディに対し ±0.71 なのもボディ相対で辻褄が合う。
- レベルは 0x00 の辺が1本も無い。4トラックとも純粋な 0x04 連鎖で、
  全ノードが位置(0,0,0)、頂点がワールド座標。継承が無い=兄弟の並びで正しい。

### Blenderへの反映

インポート時に親子付けするようにした (`parentBlenderObjectsByNodeRelation`)。
ノードの子とその兄弟連鎖を、そのノードのBlenderオブジェクトの子にする。

- 子の `matrix_local` は親からの相対で、ノードのトランスフォームそのもの。
  よって軸変換(Y-up→Z-up)は根オブジェクトのみに掛ける。
  子にも掛けると階層の深さの回数だけ適用されてしまう。
- `matrix_parent_inverse` は単位行列に戻す。既定のままだと
  Blenderが見た目を維持するためのオフセットを入れてしまう。
- エクスポートは親を持つオブジェクトの `matrix_local` をそのまま書き戻す。
  軸変換を戻すのは根のみ。
- レベルは 0x00 の辺が無いので、この変更の影響を受けない。

Blender 4.0 / 4.2 / 4.3.2 / 5.0.1 で、無編集の往復のノード配列一致は
変更前と同数(105一致 / 29差分)。差分29件は下記の
Model Pointers `unk_0x18` 未書き出し(ライト系メッシュ)によるもので、
これは後述の対応で解消した。

| トラック | 変更前 | 変更後 |
|---|---|---|
| DES_SS1 | 594 | 902 |
| MNT_SS2 | 483 | 1102 |
| RIVIERA | 120 | 628 |
| SNW_SS3 | 326 | 849 |

テクスチャも Texture Index で同名 `<NAME>.TXR` から解決され、ほぼ全メッシュに適用される。

### Model Pointers `unk_0x18` の追加ブロック

メッシュは Face と Model Pointers の間に 0x20 のブロックを持つことがあり、
`unk_0x18` がそのオフセットを保持している。読み書きするようにした。

判別条件は `unk_0x18 == Model Pointers Offset - 0x20`。サンプル全3810メッシュで、

- 73メッシュ: 上式が成立。全て車のライト系(頂点4個・面1個のビルボード)。
  73件とも Face の終端直後にブロックが始まり、内容も全て同一で
  `0.0, 1.0` の4組(8 float)。頂点1個あたり2 float の何か。
- 3737メッシュ: `unk_0x18` は 0xA 等の小さな値でオフセットとして成立しない。
- 中間的なケースは0件。判別は曖昧さ無く確定する。

意味は未解読なので、生の32bit語のまま保持して書き戻す。
Blenderオブジェクトのカスタムプロパティ `Model Extra Block` に載る。

これで **往復のノード配列一致は 105/29差分 → 134/0差分**。
Blender 4.0 / 4.2 / 4.3.2 / 5.0.1 で同結果。

### Face Count 1 のメッシュ (ゲームでフリーズした件)

ゲーム実機確認で、`_light` 系を差し替えると走行画面でフリーズすることが判明
(bk_light / de_light(砂漠) / sn_light(雪) で再現)。

原因は **Face Count 1 のメッシュのインデックスが32bit**だったこと。

| | Face Count | face領域の先頭16バイト |
|---|---|---|
| 元 | 1 | `03000000 02000000 01000000 00000000` (32bit×4) |
| 旧エクスポート | 6 | `0000 0100 0200 0200 0100 0300` (16bit×6) |

サンプル全体で Face Count = 1 は98メッシュ。全て頂点4個のビルボードで、
車のライト類がこれに当たる。通常のメッシュは Face Count が3の倍数で
16bitインデックス列。どちらの符号化になるかの判定条件は未解読。

対応: 面を編集していないメッシュは face領域を元のバイト列のまま書き戻す。
Face Count も元の値を維持する。法線・トランスフォームで既に使っている
「編集されていなければ元の値を保持する」方式と同じ。

この不具合は「ノード配列一致」という指標では捕捉できなかった。
Model Pointers はメッシュ側にありノード配列に含まれないため。
検証をメッシュ記述全体(各Count / face領域 / マテリアル / Draw Options /
`unk_0x18`ブロック)の比較に広げ、136ファイル・329メッシュ全一致を確認した。

### 実機確認で確定したこと

修正版(COROLLA全16ファイル無編集リパック)をゲームに入れて走行、正常動作を確認。
自己完結の検証しか無かった状態から、**ゲームが本ツールの出力を受け付けることが
初めて実証された**。同時に下記が確定した。

- **メッシュ内のセクション順は無害**。この確認版は元が `Vertex,Material,Face` の
  ファイルを `Material,Vertex,Face` に並べ替えたまま動作している。
  ゲームは Model Pointers のオフセットを見ており、並び順には依存しない。
  よって順序保持はバイト一致のためだけの項目で、**正しさには不要**。
- **UVの `-0.0`/数ULPのずれも無害**。
- `unk_0x18` のブロックの扱いは正しい。
- ノード階層(親子付け)を入れた状態のエクスポートも正常。

未検証: 法線の相違(`tree_a`〜`tree_f`, `Char\*.MDL`)。COROLLA には該当が無いため
この確認では触れていない。→ 下記で解決。

### 法線が往復で保たれなかった8ファイル

原因は **Blenderが保持できない法線**だった。

| ファイル | 該当 | ファイル内の値 |
|---|---|---|
| `tree_a`〜`tree_f` | 各4頂点 | `(0, 0, 0)` 長さゼロ |
| `Char\A.MDL` `Z.MDL` | 全頂点 | `(0, NaN, 0)` 生の語は `00000000 FFE6E632 00000000` |

Blenderはカスタム法線を正規化するため、長さゼロは面の法線に、非有限値は既定値に
置き換わる。つまり**ファイルの値はユーザーに一度も見えていない**ので、
ユーザーが編集したはずが無い。にも関わらず書き戻し側は
`if original_normal.length > 0.0` の条件を通らず、保持処理に到達していなかった
(NaN も `NaN > 0.0` が偽になるため同じ穴に落ちる)。

対応: 比較できない法線(長さゼロ / 非有限)は元の値をそのまま書き戻す。
インポート時に法線を退避している属性 `sr2_normal` は、
長さゼロも NaN も**ペイロードまでビット単位で保持できる**ことを確認済み。

検証範囲も頂点データ(位置 / 法線 / UV)まで拡張した。
136ファイル・329メッシュで、位置・法線・face領域・マテリアル・Draw Options・
`unk_0x18`ブロック・各Count が全一致。Blender 4.0 / 4.2 / 4.3.2 / 5.0.1 で同結果。
残る不一致は UV のみ(231メッシュ)。→ 下記で解決。

### UVの往復ずれ

法線と同じく「編集されていなければ元の値を保持」する方式を UV にも適用した。
インポート時の UV を属性 `sr2_uv` に退避し、書き出し時に一致すれば元の値を戻す。

ずれの正体は2つ。

- V=0.0 が **-0.0** になる。`-(v - 1.0)` の反転を2回通すと、
  1回目で `1.0` になった値を2回目で `-(1.0 - 1.0)` = `-0.0` と符号付きゼロにする
- Blenderが単精度で保持するため、二重丸めで最下位ビットが動く

これで **231メッシュ → 7メッシュ**。

残る7メッシュ(KEROLLA の bk_light / bkfire / ft_light / hazard)は、
UV座標に **シグナリングNaN** が入っているもの。サンプル全UV座標 43,024個のうち
28個が該当する。`struct.unpack('<f', ...)` で Python の float (double) にした瞬間、
ハードウェアの float32→double 変換がクワイエットNaNに変えてしまう
(`0xFFB2B2B2` → `0xFFF2B2B2`、差はビット22のみ)。
退避先を工夫しても復元できず、頂点データ全体を生の32bit語で持ち回る必要がある。
NaN であることは変わらず、対象はテクスチャ無しビルボードのU座標なので、
費用に見合わないと判断し対応しない。

### UV編集時の注意

MDLは頂点あたり1組のUVを持つが、Blenderはコーナー(ループ)ごとに持つ。
そのためUVを編集する場合、**同じ頂点を共有する全コーナーに同じ値**を
与えないとファイルに反映されない(書き出しは最後に見たコーナーを採用する)。
これは形式由来の制約で、今回の変更とは無関係。

# 8. テクスチャ読み取り

importしたモデルにテクスチャを適用したい。

SR2ToolsにTXR(TEX)ファイルの解析コードが既にある。

- 解析本体: `src/io_scene_srally2mdl/SR2Tools/texture_classes.py`
  RTEX / RHBG / RTXR / MTEX の4種のシグネチャに対応。
  依存は`struct`と同梱の`bmp_handler`/`unyakuza`のみなので、Blender内でもそのまま動く。

- 呼び出し口: `src/io_scene_srally2mdl/SR2Tools/texture_tool.py` の `convertTXRtoBMPlist()`
  ただしPILを使用しており、Blender同梱のPythonにPILは無い(numpyはある)。
  BMP/PNGを経由せず、解析した画素バイトを`bpy.data.images`へ直接渡す形にする必要あり。

- 各モジュールが絶対import (`from bmp_handler import BMPv5` 等) のため、
  パッケージ内から使うには相対importへの変更が必要。

## 対応付けの解読結果

Node Transform の 0x0C (旧 `unk_0x0C`) が **Texture Index** だった。
5つのfloatの1つとして読んでいたため、NaN や 1.4e-45 (非正規化数) に見えていた。
32bit整数として読むと -1(テクスチャ無し) / 0 / 1 / 2。

- 提供された r_corolla の正解 (body, ホイール4, body, ホイール, 窓2) に対し
  `[0, 1, 1, 1, 1, 0, 1, 2, 2]` で完全一致。
- `-1` は色のみで描画されるメッシュ(ライト類, brake)。UVが1点に潰れている点とも一致。
- RIVIERA/finish.mdl は `[1, 0]` で、2枚のテクスチャを逆順に使う。
- DC版でも同じ値・同じ意味で成立。PC版固有ではない。

車はモデル同名のテクスチャファイルを持たず、下記を参照する。

- 0 = 車フォルダの `body.txr`
